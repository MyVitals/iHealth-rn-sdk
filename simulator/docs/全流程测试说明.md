# 用模拟板做 SDK / App 测试：全流程说明

模拟板把"没有真机"这件事解决了，剩下的是怎么把测试做成可重复、可无人值守、结果可回填的流程。
流程分五层，**从 L0 往上做，每一层通过了再上一层**；一个只做 App 集成的团队做到 L1–L2 就够，L3–L4 是 SDK 组和测试平台在用的。

| 层 | 内容 | 需要 | 时间 |
|---|---|---|---|
| L0 协议自测 | 不用硬件，Mac 上让 SDK 侧逻辑和设备协议核心互相跑一遍 | 固件源码（SDK 组内部） | 秒级 |
| L1 板子 + SDKDemo 自动测试 | 手机上的 SDKDemo 以 `-autotest` 启动，自己扫描 / 连接 / 认证 / 跑指令，板子串口对账 | 板子、iPhone、SDKDemo 源码 + 授权 .pem | 每机型每场景 1–3 分钟 |
| L2 App 执行组 | 对真正的 App（MyVitals）按用例 Excel 跑 XCUITest / UIAutomator 执行组，结果回填用例表 | 板子、手机、App 源码、测试账号 | 每机型 1–6 小时 |
| L3 Android | 同 L1 / L2 的 Android 版（RN SDK AutoTest、Android 原生 SDK、MyVitals Android） | 第二块板子、Android 手机、adb | 同上 |
| L4 测试 Agent | 打包机上的任务队列 + 两条通道（iOS / Android）自动领任务、预检、跑、判读、写报告发飞书 | 打包机、Claude 接口 | 无人值守 |

---

## L0 协议自测（Mac，无硬件）

```bash
cd firmware/ihealth_sim/host_test && ./run.sh      # 末行 ALL PASSED
```

`sdk_sim.py` 按 SDK 源码逐段移植了 App 侧逻辑（FA 组包、FB 解密校验、FC 加密、CTR 解密、分包解析），驱动协议核心 `sim_cli`
走完 认证 → 对时 → 设备信息 → 分包传记录 → 删除 → 重连 → 错误应答，并模拟 20 字节 BLE 分片。末尾自动跑全部场景矩阵。
**改了协议代码必须先过这一关**，再去碰板子。

## L1 板子 + SDKDemo 自动测试（iPhone）

前提：板子已刷固件；iPhone 解锁、信任电脑、开发者模式打开；SDKDemo 工程能编译并能装到这台手机
（SDKDemo 的 bundle id `com.iHealthSDK.SDKDemo` 和配套授权 .pem 必须一致，否则 SDK 什么都扫不到）。

```bash
cd firmware/ihealth_sim/host_test
./phone_test.sh --build --model KN550BT                      # 第一次：编译安装 Demo，板子切机型，跑一遍 → PHONE TEST PASSED
./phone_test.sh --model KN550BT --scenario slow_4s           # 指定场景
./scenario_matrix.sh --model KN550BT                         # 全部场景，出 matrix.md
```

原理：Demo 的 `AppDelegate` 里有 `IHSDKAutoTest`，App 以 `-autotest <机型>` 启动时不进首页，直接 授权 → 扫描 → 连接 / 认证 → 各业务指令 → 断开，
每步 10–30 秒超时，日志写沙盒 `Documents/autotest.log`（含 SDK 的 app→device / device→app 十六进制）。脚本用 `devicectl` 拉起 App、拉回日志，
同时抓板子串口，最后并排打印。输出在 `host_test/build/phone/`。

换电脑 / 换手机 / 换板子只改环境变量：`IH_PHONE_ID`（CoreDevice 标识，`xcrun devicectl list devices` 可查）、`IH_BOARD_PORT`、`IH_SDK_WORKSPACE`。

**场景矩阵的判定口径**（每个场景都有"板子行为 → App 预期"）：

| 场景 | 板子行为 | 预期 SDK / App 行为 |
|---|---|---|
| `normal` | 默认数据、设备固件 1.0.0 | 全流程通过 |
| `fw_old` / `fw_new` | 设备上报固件 0.9.0 / 2.1.0 | App 读到对应版本，功能不受影响 |
| `proto_mismatch` | 协议串改成未知值 | 原样透传，不崩溃 |
| `auth_fail` / `auth_badr1` | 认证阶段回错 / R1' 改坏 | 连接失败并给出认证错误，不卡死 |
| `no_reply_0x24` 等 | 某指令不应答 | 对应指令 3 秒超时错误，其余功能正常 |
| `slow_2s` / `slow_4s` | 业务回包延迟 2 / 4 秒 | 2 秒仍通过；4 秒触发 SDK 超时 |
| `bad_checksum` | 回包校验和错 | 帧被丢弃 → 超时，不崩溃 |
| `drop_after_auth` / `drop_mid_transfer` | 认证后 / 传输中断开 | App 收到断开通知，传输中断被正确报错 |
| `empty` / `full` | 0 条 / 每组 199 条 | 条数一致，大数据量分包收齐 |
| `badtime` / `extreme` / `clock_skew` | 非法时间、极值、设备时钟错 | 时间兜底生效、条数不丢、对时后纠正 |
| `lowbatt` / `error_state` | 低电 / 错误状态 | 状态字段正确、有提示 |

## L2 App 执行组（MyVitals iOS 为例）

用例来自产品的用例 Excel（每机型一份，见 `docs/myvitals_cases/<机型>.md`），按"执行组"组织：一个执行组 = 一个 XCUITest 方法 + 板子命令 + 环境变量 + 覆盖的用例编号。

```bash
cd firmware/ihealth_sim/host_test/myvitals
IH_BOARD_PORT=/dev/cu.usbmodemXXXX python3 mv_suite.py --model kn550bt            # 全部执行组
python3 mv_suite.py --model kn550bt --groups add_bind_normal,sync_normal          # 指定组
python3 mv_report.py <结果目录>                                                   # 回填 Excel + 生成报告
```

每组结果 PASS / FAIL + 失败原因 + 截图 + 流程图（`flowmap.html`）。失败必须判读成四类之一：

| 判读 | 含义 | 处理 |
|---|---|---|
| **App 缺陷** | App 行为和用例预期不一致，且板子日志证明设备侧正确 | 起缺陷单（云效），附板子串口 + App 日志 |
| **脚本问题** | 元素定位、等待时间、用例理解有误（例：测试账号温度单位是 ℉，按 ℃ 找元素失败） | 改测试脚本，重跑 |
| **环境问题** | 手机隧道断、串口中止、测试服务器连不上、板子被别的 App 抢连 | 修环境后重跑，不计入结果 |
| **平台差异** | iOS / Android 产品定义就不同 | 记录，不算缺陷 |

跑之前的约定：先关掉手机上其他会自动连设备的测试 App；测试账号不要用会改真实用户数据的组（`no_temp_data` 之类默认跳过）；
一台手机一次只跑一个机型；日志、截图、结果 JSON 一起归档，报告里写清被测版本（App 版本 + SDK 版本 + 固件版本）。

## L3 Android

和 L1 / L2 对称，用第二块板子 + Android 手机（`adb devices` 已授权）：

```bash
cd firmware/ihealth_sim/host_test/rn
IH_BOARD_PORT=/dev/cu.usbmodemYYYY ./android_regress.sh kn550bt po3 bg1s hs2s     # RN SDK AutoTest，逐机型切板子、读 MAC
cd ../android_native && IH_BOARD_PORT=... python3 run_android_native.py --model KN550LT   # Android 原生 SDK
```

Android 要注意：系统设置类用例（蓝牙、网络、权限、锁屏、12/24 小时制）脚本可以改，但**测完必须恢复**；
ColorOS 等定制系统 `pm grant/revoke` 会被拒，权限用例只能走设置页 UI；手机上多账号时固定用测试账号。

## L4 测试 Agent（无人值守）

打包机上的 Agent 把 L1–L3 包成任务：任务 JSON 写明被测版本、机型、执行组、预算，丢进队列；两条通道（iOS 一块板 + iPhone，Android 一块板 + Android 手机）
各自领任务，**先预检**（测试服务器、手机连接 / 解锁、串口有固件回复、设备锁、磁盘、代码源），预检不过就 10 分钟后重试、不花模型费；
跑完由模型逐组判读、写补充报告、起缺陷单草稿，报告发飞书。时间窗按打包机作息（断电前收尾，没跑完的组列在报告里，下次续跑）。

日常只需要三件事：看每天的报告；对 Agent 起的缺陷草稿做确认；有新版本时提交任务。任务模板、队列目录、通道状态页见 Agent 的 README。

BG5S（11-05）就是按这份清单接入的：规格 1 天、固件 + Mac 自测 84 个用例半天、SDKDemo `-autotest BG5S` 真机 10 步通过。

## 新机型接入清单

1. 协议文档（`docs/protocols/<机型>.md`）：从 SDK 源码和协议 xls 整理出 UUID、广播格式、认证、指令表。
2. 固件：`lib/ihproto/ih_<model>.c` + 场景表；L0 的 `sdk_sim.py` 加对应的 App 侧逻辑，`run.sh` 过。
3. 刷板，`model <key>` 切过去，L1 用 SDKDemo `-autotest <机型>` 跑通 normal。
4. 用例 Excel → `docs/myvitals_cases/<机型>.json`，写执行组 `mv_runs_<model>.py`，L2 跑通。
5. manifest.json 加机型，CHANGELOG 记版本，发新固件。

## 常见坑（都踩过）

- 手机被系统反复拉起的演示 App 抢连接 → 执行组随机掉线：卸掉或禁用多余的测试 App。
- 打包机休眠（`pmset -g` 的 sleep 不是 0）→ 进程变慢、隧道断：关休眠，常驻进程用 `caffeinate`。
- 串口被内核中止（读卡 15 分钟、乱码）：串口抓取加硬超时，按环境问题重跑；板子反复出问题就换板。
- 同一块板子切机型后 iOS 扫不到：机型地址已经分开了，但 App 里旧绑定要先解除。
- 新板子出厂固件不是模拟器：串口只打 `50%R/G/B`，刷固件即可。
